# SQLite store with a global revision

Status: accepted, 2026-10.

## Context

The control plane runs on one host, and one person operates it. Watch semantics
(list, then watch from a point without missing events) are the foundation for
controllers, the node and `hangar wait`.

## Decision

- **SQLite** through modernc (pure Go, no cgo), behind an `internal/store`
  interface that leaks no SQLite semantics (in particular, no multi-object
  transactions), so a Postgres implementation can replace it when the control
  plane needs high availability.
- **A global, monotonically increasing revision**, as in etcd. Every write bumps
  it, and an object's `resource_version` is the revision of its last write.
- **An events table** records every write. `Watch(since)` replays from it and
  then hands over to an in-process bus. Old events are compacted; asking for a
  compacted revision returns an error that tells the client to re-list.
- **Objects are stored as proto binary**, so renaming a field never touches
  stored data. A debug dump command decodes it for humans.
- **Writes are serialized** behind one mutex.
- **Label selectors** are evaluated in memory until volume demands an index.
- **Queries are generated by sqlc** from SQL checked against the schema at
  generate time. **Migrations** are goose-format SQL files embedded in the
  binary and applied at startup; sqlc reads the same files as its schema.

Not Postgres: it would be another service to run, upgrade and back up, for high
availability a single host cannot provide. Not embedded etcd: a single etcd node
brings its operational quirks without its benefits.

## Consequences

- Backups are continuous through litestream.
- A future Postgres backend gets its own query set under
  `internal/store/postgres`; the revision and event design carries over.
